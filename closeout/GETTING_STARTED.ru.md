# Closeout: руководство для начинающих

[中文](GETTING_STARTED.zh-CN.md) | [English](GETTING_STARTED.en.md) | **Русский**

Closeout выполняет доказательную сверку проекта после завершения этапа: сопоставляет код, реальное поведение, документацию, правила Agent, разрешённую память и остаточные файлы рабочего пространства.

Это не обычный сортировщик файлов. Он не удаляет файлы, ветки или worktree без осознанного подтверждения.

## 1. Установка

```bash
git clone https://github.com/Jorgut/closeout-skill.git
cd closeout-skill
python3 scripts/install_closeout.py --all-platforms --commands
```

Последняя команда показывает план. Если конфликтов нет, примените установку:

```bash
python3 scripts/install_closeout.py \
  --all-platforms \
  --commands \
  --apply \
  --confirm
```

Полностью закройте и снова откройте Codex, OpenCode или Claude Code.

## 2. Где вводить команду

### Codex

В Codex нет пользовательской команды `/closeout`. Используйте:

```text
$closeout
```

Или обычный запрос:

```text
Используй Closeout и проверь, соответствуют ли друг другу код, README и правила Agent.
```

### OpenCode или Claude Code

```text
/closeout
```

Также можно написать:

```text
Выполни Closeout для этого проекта, но пока ничего не удаляй.
```

## 3. Первый безопасный тест

Откройте небольшой Git-проект с кодом и README, затем введите:

```text
$closeout docs-sync. Проверяй только код, README и файлы правил. Не меняй память и ничего не удаляй.
```

В OpenCode или Claude Code замените `$closeout` на `/closeout`.

Прочитайте статусы всех шести плоскостей фактов. Если указаны кандидаты на удаление, они останутся на месте до отдельного подтверждения после отчёта.

## 4. Выбор режима

### `docs-sync`

Для обычного завершения разработки и сверки документации:

```text
$closeout docs-sync. Сверь команды запуска, порты и описанные функции с текущей реализацией.
```

### `knowledge-closeout`

После завершения функции или этапа, чтобы следующая сессия получила точный контекст:

```text
$closeout knowledge-closeout. Синхронизируй документацию, правила и только ту память, которую платформа явно разрешает изменять.
```

Без поддерживаемого и разрешённого интерфейса Closeout не должен самостоятельно записывать память.

### `release-closeout`

После PR, развёртывания или релиза:

```text
$closeout release-closeout. Отдельно проверь состояние кода, удалённого репозитория, развёртывания и реального пользовательского интерфейса.
```

Состояния различаются: `draft`, `PR`, `merged`, `deployed`, `live-verified`, `knowledge-closed`, `cleaned`. Слияние не означает развёртывание, а развёртывание не означает проверку живой системы.

### `workspace-audit`

Только для проверки нескольких проектов:

```text
$closeout workspace-audit. Только читай и ищи конфликты документации и правил; не записывай изменения в соседние проекты.
```

## 5. Как читать отчёт

| Плоскость | Что проверяется |
| --- | --- |
| `code` | Исходный код, конфигурация, schema и тесты |
| `runtime` | Что реально получают пользователи или сервисы |
| `docs` | Точность README и документации |
| `rules` | AGENTS.md, CLAUDE.md и другие активные инструкции |
| `memory` | Разрешённые знания между сессиями |
| `workspace` | Временные файлы, копии, ветки и worktree |

Статусы:

- `verified-current`: проверено и актуально
- `changed-and-verified`: исправлено и повторно проверено
- `pending`: доказательств недостаточно, завершение заявлять нельзя
- `out-of-scope`: не входит в текущую задачу
- `not-applicable`: для проекта эта плоскость отсутствует

## 6. Почему для очистки нужно отдельное подтверждение

Сначала Closeout показывает полный отчёт и кандидатов на очистку: старые планы, резервные копии, ветки или worktree. После чтения отчёта пользователь подтверждает конкретные элементы.

```text
Пользователь: $closeout knowledge-closeout
Agent: показывает доказательства и кандидатов на удаление
Пользователь: Я прочитал отчёт. Удали A и B, но сохрани C.
Agent: выполняет разрешённую очистку, повторно проверяет проект и дополняет отчёт
```

Первоначальная фраза «заверши и почисти» не является финальным подтверждением. Это защищает единственные экземпляры работы от случайного удаления.

## 7. Примеры

```text
$closeout docs-sync. Проверь новую авторизацию, описание переменных среды и команду тестирования.
$closeout knowledge-closeout. Подготовь точную передачу проекта и перечисли незавершённое без ложных заявлений.
$closeout release-closeout. Проверь commit GitHub, запись развёртывания и живую страницу; недоступное отметь pending.
$closeout workspace-audit. Работай только на чтение и не меняй файлы, память, ветки или worktree.
```

## 8. Устранение неполадок

### Нет `/closeout`

- В Codex используйте `$closeout`.
- В OpenCode и Claude Code установщик должен запускаться с `--commands`.
- Полностью перезапустите приложение.
- Проверьте ссылки:

```bash
ls -l ~/.config/opencode/commands/closeout.md
ls -l ~/.claude/commands/closeout.md
```

### Кандидаты не были удалены

Это нормальная защита. Прочитайте предварительный отчёт и явно подтвердите только разрешённые элементы.

### Почему указан `pending`?

Нет прямого доказательства: доступа к production, прав на удалённый репозиторий или выполненных тестов. Честный `pending` надёжнее ложного статуса завершения.

### Проверка установки

```bash
ls -l ~/.agents/skills/closeout/SKILL.md
ls -l ~/.codex/skills/closeout
ls -l ~/.config/opencode/skills/closeout
ls -l ~/.claude/skills/closeout
```

Последние три пути должны вести к одному основному экземпляру.
